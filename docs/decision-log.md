| D-1  | 29 Sep    | Initial idea for the project                                                              | Is Hot reload a feasible way to dynamically load code? Is hot reload able to support the potential research into dynamic loading?<br />**No** in both cases                            | Hot reload is limited to a single user in debug mode. Because research with multiple users is the direction the project is going in, this option is dropped                                                                                                                                    | Look for other ways of loading code at runtime in Flutter                                                                                                                              |
| D-2  | 6 October | What medium will be used for research and exploration                                     | I will use a tower defence game to explore options and research effects of dynamic loading of code                                                                                     | A game is the perfect test, test users will be enticed to use the game for its gameplay features (assuming it will be fun) and the results can be extrapolated and applied theoretically to other use cases. The game would act as a proof of concept                                          | How can I actually implement a game in Flutter?                                                                                                                                        |
| D-3  | 13 Oct    | How can the game be implemented in Flutter                                                | I will use the Flame engine to develop the game                                                                                                                                        | It is an actively supported game engine for Flutter, perfect for this use case                                                                                                                                                                                                                 | How can I use dynamic loading with the game using Flame                                                                                                                                |
| D-4  | 20 Oct    | How can code be loaded at runtime in Flutter in order to support research/experimentation | Multiple ways of achieving it. See minutes from meetings 2 to 4. Decided on dart_eval to inject runtime code, Shorebird to update test application to simplify updates for test users. | Provides the ideal setup, we can stick with a single language (Dart) and it is true dynamic loading compatible. It can be used with Flame as proved by the prototype (see the [prototype branch](https://github.com/nexuma/tower-defence-final-project/tree/prototype) on the main repository) | Start writing basic requirements and planning the base of the game. This is so that the game is the perfect testbed and base to build on, no matter what direction the research takes. |
| D-5  | 9 Nov     | Prototype usage/purpose?                                                                  | The prototype will not be used and is only on the repo for archival reasons                                                                                                            | The prototype was generated quickly with AI assistance as a proof of concept, it was not designed to be maintained, and I don't know it well enough to build on.                                                                                                                               | Rebuild the game on master; the prototype still counts as evidence.                                                                                                                    |
| AD-1 | 9 Nov     | Where does the game logic live?                                                           | The state lives in a Dart model, not a Flame component                                                                                                                                 | This separation gives more control over the state and makes it easier to calculate and test things, all outside of Flame                                                                                                                                                                       | Skips a lot of things Flame makes easier to do, so a bit more work, but less time writing tests                                                                                        |
| AD-2 | 9 Nov     | How is the communication between dart_eval and engine handled?                            | There is a CombatLogic interface which does the talking with the sandbox                                                                                                               | This separation makes it easy to test multiple versions of the sandbox, separates any problems and makes sure if the sandbox fails we can fall back on another method of getting the combat logic                                                                                              | Easier extendability and better reliability.                                                                                                                                           |
| AD-3 | 9 Nov     | How much control does Flame have over input?                                              | It only passes input to the engine, it does not update itself from the input.                                                                                                          | This means Flame is purely there to render the game, and rules/constraints are only applied in a single place.                                                                                                                                                                                 | Easier to test and experiment without Flame features or architecture getting in the way.                                                                                               |
| AD-4 | 9 Nov     | How is the view updated?                                                                  | The reader called ViewSync pulls the model every frame                                                                                                                                 | Pull for what is displayed so that the view is always up to date and push for what is counted to make sure crucial information is passed immediately                                                                                                                                           | Better control and separation. Maybe better performance, needs to be tested and might be adjusted                                                                                      |
| AD-5 | 9 Nov     | How is input controlled?                                                                  | There is a separate InputHandler which receives the input from Flame.                                                                                                                  | Same reasons as above. Also we can change how the input is read and controlled more easily                                                                                                                                                                                                     | Same reasons as above. We have more control.                                                                                                                                           |
