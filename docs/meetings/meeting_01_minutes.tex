\section{Issues Discussed \& Solutions Agreed}

\begin{itemize}[leftmargin=*]
    \item \textbf{Flutter Hot Reload and debugging:} Hot Reload injects updated source code into a running Dart VM in Debug mode without losing application state. It is limited to debug builds and cannot modify \texttt{main()} or native code.
    \item \textbf{Production code updates:} Shorebird was explored as a tool for remotely patching Dart logic in release mode using production over-the-air updates.
    \item \textbf{Deferred components:} Flutter's \texttt{deferred as} mechanism and Android Dynamic Feature Modules can split compiled binaries and reduce initial memory usage.
    \item \textbf{Server-driven UI:} The \texttt{rfw} package can render declarative UI dynamically from binary \texttt{.rfw} or text \texttt{.rfwtxt} definitions sent by a server.
    \item \textbf{Modular game architecture:} Flame was identified for the game loop, with modular asset loading and possible embedded scripting through \texttt{lua\_dardo} or \texttt{flutter\_js}.
    \item \textbf{JIT and AOT constraints:} JIT is used in Debug mode and supports dynamic execution at a memory and performance cost. AOT is used in Release mode and produces statically compiled native code without the JIT compiler.
    \item \textbf{Academic bypasses:} Potential approaches included retaining JIT in Debug or Profile mode with \texttt{vm\_service}, loading dynamic native libraries through \texttt{dart:ffi}, and forking the Flutter C++ engine to re-enable \texttt{Isolate.spawnUri()}.
\end{itemize}
