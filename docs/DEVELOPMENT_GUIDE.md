# Tower Defence Development Guide

This document explains the Flutter project structure, the Flutter runtime
model, the Flame/dart_eval proof of concept, and how to run it on a physical
Android or iOS device.

## 1. What Flutter is

Flutter is a UI and application framework written in Dart. A Flutter
application is built from widgets, which describe what should appear on
screen. Widgets are arranged in a tree:

```text
MaterialApp
└── GameWidget
    └── FlameGame
        ├── TowerComponent
        └── EnemyComponent
```

Flutter repeatedly builds and paints this tree when state changes. Dart code
normally runs ahead-of-time (AOT) in release builds and is compiled into the
application. This is why a release Flutter app cannot simply download a new
`.dart` file and execute it as native Dart.

During development, Flutter provides:

- **Hot reload**: injects many code changes into a running debug application
  while preserving its current state.
- **Hot restart**: restarts the Dart application and loses its current state.
- **Debug mode**: includes diagnostics and development features.
- **Profile mode**: is intended for performance measurement.
- **Release mode**: is optimized for distribution and uses compiled code.

Flutter renders its own controls and drawing rather than translating every
widget into a platform-native control. Platform folders still provide the
Android and iOS application hosts, permissions, build settings, and native
entry points.

## 3. How this application starts

The entry point is [`main.dart`](../lib/main.dart):

```dart
void main() {
  runApp(const TowerDefenceApp());
}
```

`runApp` attaches the root widget to Flutter's rendering pipeline.
`TowerDefenceApp` creates a dark `MaterialApp`, then places a Flame
`GameWidget` at the home route:

```dart
home: GameWidget(game: TowerDefenceGame()),
```

`GameWidget` is the Flutter-to-Flame adapter. It lets a Flame game render
inside the Flutter widget tree. Flutter owns the application window and
widget lifecycle; Flame owns the game loop and game components inside that
widget.

## 4. How the Flame baseline works

[`TowerDefenceGame`](../lib/game/tower_defence_game.dart) extends
`FlameGame`. Its main responsibilities are:

1. **Loading components**: `onLoad` creates a tower at `(160, 240)` and an
   enemy at `(40, 240)` with 100 health, plus its firing-range indicator.
2. **Adding components**: `add(tower)`, `add(enemy)`, and the range component register the objects
   with Flame so they are updated and rendered.
3. **Running the loop**: Flame calls `update(dt)` repeatedly. `dt` is the
   elapsed time since the previous update, in seconds.
4. **Moving the enemy**: the enemy advances in a straight line toward the
   tower at 40 game units per second and stops at the 50-unit firing range.
5. **Scheduling attacks**: `_attackTimer` accumulates `dt`. Once it reaches
   0.5 seconds, the game performs one sandbox evaluation.
6. **Applying results**: only a validated `DamageInstruction` is applied to
   the enemy.

`TowerComponent` and `EnemyComponent` extend Flame's
`PositionComponent`. They have a position and size, and override `render`:

- The tower draws a blue rectangle.
- The enemy draws a red circle while alive.
- The enemy draws a grey circle after its health reaches zero.
- `TowerRangeComponent` draws a translucent grey circle around the tower.
- The game draws the five most recent events in a dark panel at the bottom,
  including spawning, range entry, firing, destruction, and sandbox errors.

The enemy's `applyDamage` method clamps health between 0 and 100. The current
baseline intentionally has no input, waves, gold, tower placement, or
incubator mechanics yet.

## 5. How the Flame/sandbox bridge works

The bridge is deliberately value-based. It does not expose Flame components
or Flutter objects to the evaluated code.

### 5.1 State going into the sandbox

[`CombatState`](../lib/bridge/bridge_models.dart) contains only:

- tower X coordinate;
- tower Y coordinate;
- enemy X coordinate;
- enemy Y coordinate;
- enemy health.

`toSandboxArguments()` converts these fields into the primitive argument list
expected by the evaluated function.

The game creates a fresh snapshot on each attack:

```text
TowerComponent/EnemyComponent
        |
        v
CombatState
        |
        v
primitive dart_eval arguments
```

### 5.2 Evaluation

[`DamageSandbox`](../lib/bridge/sandbox_runner.dart) loads the local
[`damage.dart`](../assets/scripts/damage.dart) module through Flutter's asset
system, then evaluates its function using `dart_eval`:

```dart
int calculateDamage(
  double towerX,
  double towerY,
  double enemyX,
  double enemyY,
  int enemyHealth,
)
```

The function returns:

- `0` if the enemy is dead;
- `0` if the squared distance is greater than `2500`;
- `10` otherwise.

The range check uses squared distance so it does not need a square-root
operation. A squared range of `2500` corresponds to a range of 50 game units.

### 5.3 Validation coming out of the sandbox

Before evaluation, the runner rejects non-finite coordinates and negative
health. After evaluation, `DamageInstruction.fromSandboxResult` requires the
result to be an integer from 0 through 100.

If evaluation or validation fails, `SandboxEvaluationException` is raised.
The game catches that specific exception, stores it in `lastSandboxError`, and
does not mutate enemy health. This keeps a malformed sandbox result from
becoming a successful-looking game instruction.

The complete flow is:

```text
Flame update(dt)
  -> every 500 ms
  -> create CombatState
  -> validate input
  -> evaluate calculateDamage in dart_eval
  -> validate integer damage result
  -> apply damage to EnemyComponent
```

This is a synchronous proof of concept. A later version should measure the
evaluation time and memory allocation, and may need to move expensive work
off the critical frame path. The module is currently bundled as an asset to
simulate downloaded code locally; replacing the asset loader with a verified
network loader is a later step.

## 6. Dependencies

The important dependencies in [`pubspec.yaml`](../pubspec.yaml) are:

- `flame`: game loop, component system, rendering integration, and
  `GameWidget`.
- `dart_eval`: runtime Dart evaluation used for the sandbox experiment.
- `flutter_test`: Flutter's unit and widget test framework.
- `flutter_lints`: static analysis rules.

After changing dependencies, run:

```sh
flutter pub get
```

Do not edit `.dart_tool/package_config.json` or other generated package files
by hand.

## 7. Testing locally

From the project root:

```sh
flutter pub get
dart format lib test
flutter analyze
flutter test
```

The current tests are in
[`test/bridge_test.dart`](../test/bridge_test.dart). They verify:

1. an in-range living enemy receives 10 damage;
2. an out-of-range enemy receives 0 damage;
3. invalid state such as `NaN` coordinates is rejected;
4. the root app actually contains a Flame `GameWidget`.

For a single test file:

```sh
flutter test test/bridge_test.dart
```

For more detailed output:

```sh
flutter test --reporter expanded
```

## 8. Testing on a physical Android device

### Prerequisites

Install:

- Flutter SDK;
- Android Studio;
- Android SDK and platform tools;
- a compatible Android SDK platform;
- a USB cable or Android wireless debugging connection.

Check the installation:

```sh
flutter doctor
flutter devices
```

Resolve any Android licenses requested by the doctor command:

```sh
flutter doctor --android-licenses
```

### USB device

1. Enable **Developer options** on the phone.
2. Enable **USB debugging**.
3. Connect the phone and accept the RSA debugging prompt.
4. Confirm that it appears in `flutter devices`.
5. From this project directory, run:

   ```sh
   flutter run -d <device-id>
   ```

   The device ID is shown by `flutter devices`.

While the app is running:

- press `r` in the terminal for hot reload;
- press `R` for hot restart;
- press `q` to stop the application.

### APK build

To produce a debug APK without starting it:

```sh
flutter build apk --debug
```

The generated APK is placed below `build/app/outputs/flutter-apk/`.
For a distributable build, configure signing before using a release build:

```sh
flutter build apk --release
```

## 9. Testing on a physical iOS device

iOS device deployment requires macOS with Xcode. The iOS project can be
generated on another operating system, but signing and running on a physical
iPhone require Apple's toolchain.

### Prerequisites

Install and configure:

- macOS;
- Xcode;
- Flutter SDK;
- CocoaPods if required by the Flutter installation;
- an Apple ID or Apple Developer team for signing.

Then run:

```sh
flutter doctor
cd ios
pod install
cd ..
open ios/Runner.xcworkspace
```

In Xcode:

1. Connect and unlock the iPhone.
2. Trust the computer on the device if prompted.
3. Select the `Runner` target.
4. Set a unique **Bundle Identifier**.
5. Select a development **Team** under Signing & Capabilities.
6. Select the connected iPhone as the run destination.
7. Allow the development certificate on the phone if iOS requests it.

You can then run from the project root:

```sh
flutter devices
flutter run -d <ios-device-id>
```

For a simulator, start one from Xcode or Simulator, then use the simulator
ID shown by:

```sh
flutter devices
```

Physical-device deployment may require the device to be trusted and the
application signing profile to be valid. Those are Apple platform
requirements, not Dart or Flame errors.

## 10. Recommended development workflow

1. Make a small change under `lib/`.
2. Format it with `dart format lib test`.
3. Run the focused test affected by the change.
4. Run `flutter analyze`.
5. Run the full `flutter test`.
6. Run on a debug device with `flutter run`.
7. Use profile mode later for performance measurements:

   ```sh
   flutter run --profile -d <device-id>
   ```

Do not use debug-mode frame timings as final performance evidence. The
`dart_eval` communication experiment should eventually record evaluation
latency, frame time, allocation, and memory behavior separately in profile
or release-like conditions.
